title: Connections and approvals
icon: plug
description: Connect custom MCP servers and handle the actions that pause a run.
---

A connection lets Fluso use another service's tools. An approval decides whether a requested action may proceed. Connecting a service and approving a tool are separate steps.

Cloud offers [managed app sign-in](/api/cloud/apps) as well as custom MCP servers. A daemon uses its own custom connections.

## Connect a custom MCP server

Start with a public HTTPS server URL. `POST /v1/mcp-oauth/probe` discovers its transport and authentication method without saving a connection.

| Server authentication | Start with |
| --- | --- |
| No authentication, bearer token, or API key | `POST /v1/mcp-oauth/connections/static` |
| OAuth with automatic client registration | `POST /v1/mcp-oauth/sessions` |
| OAuth with your own client registration | `POST /v1/mcp-oauth/sessions/byo-oauth` |

For OAuth, open the returned `authorization_url`. An `already_connected` response needs no redirect.

On Cloud, finish with the callback's `completion_proof` under the initiating account. On a daemon, `/daemon/v1/oauth/callback` completes the connection directly. Poll the returned session ID until it is `connected` or reports an error.

Read connection inventory with `GET /v1/mcp-oauth/connections`. `needs_reauth` requires the user to reconnect. Inventory alone does not prove that the external server is reachable.

## Handle a waiting run

Read `state.pending_actions` from `GET /v1/threads/{thread_id}/state`.

- For `mcp_connect`, guide the user through the requested connection flow.
- For a pending `mcp_tool`, read the approval and show its actual tool arguments for review.

After the user approves that tool call, send this body to its approval decision endpoint:

```json
{
  "decision": "allow",
  "scope": "once"
}
```

Use `decision: "deny"` to refuse it. A developer write token can make this one-time decision. Permanent permissions require a Cloud app session or a paired daemon device.

An acknowledgement saves the decision. Follow thread state or events to see work resume. Do not send another input to approve the existing request.

If the decision returns 409 or 410, read the action again. It may have changed or expired. Do not approve a replacement without reviewing it.

<Accordion title="Custom connection and tool-discovery endpoints">
  | Method and path | Use |
  | --- | --- |
  | `POST /v1/mcp-oauth/probe` | Discover transport and authentication. |
  | `POST /v1/mcp-oauth/connections/static` | Save a key-based or unauthenticated connection. |
  | `POST /v1/mcp-oauth/sessions` | Start custom OAuth authorization. |
  | `POST /v1/mcp-oauth/sessions/byo-oauth` | Start OAuth with your client registration. |
  | `POST /v1/mcp-oauth/sessions/complete` | Cloud only. Save the connection from its completion proof. |
  | `GET /v1/mcp-oauth/sessions/{session_id}/status` | Read authorization progress. |
  | `GET /daemon/v1/oauth/callback` | Daemon only. Receive the provider's OAuth callback. |
  | `GET /v1/mcp-oauth/connections` | List connections without exposing secrets. |
  | `POST /v1/mcp-oauth/connections/refresh` | Refresh Cloud registrations or daemon tool discovery. |
  | `DELETE /v1/mcp-oauth/connections/{server_id}` | Disconnect and invalidate its pending authority. |
  | `GET /v1/mcp-oauth/connections/{server_id}/tools` | Read tool descriptions, input schemas, and read-only classifications. |
  | `POST /v1/mcp-oauth/connections/{server_id}/tools` | Refresh or repair the connection before tool discovery. |

  Reusing a static connection's `server_id` updates that connection. Its `auth_method` is `bearer`, `api_key`, or `no_auth`. Only the first two accept a token. API keys use `header_name`, which defaults to `X-Api-Key`.

  Tool discovery can return saved tool information with an `error`. A 409 `CONNECTION_CHANGING` includes `Retry-After: 1`. Check the connection again after that delay.

  OAuth `pending` and `processing` are unfinished states. Handle `error`, `expired`, or `superseded` before a new sign-in attempt.
</Accordion>

<Accordion title="Approval and saved-permission endpoints">
  | Method and path | Use |
  | --- | --- |
  | `GET /v1/mcp-oauth/permissions/approvals/{approval_id}` | Read the action, status, and expiry. |
  | `POST /v1/mcp-oauth/permissions/approvals/{approval_id}/decision` | Allow or deny a tool request. |
  | `POST /v1/mcp-oauth/permissions/approvals/{approval_id}/cancel` | Dismiss the pending action without granting access. |
  | `GET /v1/mcp-oauth/permissions/mode` | Read a thread's `auto_approve` setting and `version`. Supply `thread_id`. |
  | `PUT /v1/mcp-oauth/permissions/mode` | Change it with `expected_version` and the same `thread_id`. |
  | `GET /v1/mcp-oauth/permissions/default` | Read the account default. |
  | `PUT /v1/mcp-oauth/permissions/default` | Change the default with `expected_version`. |
  | `GET /v1/mcp-oauth/connections/{server_id}/permissions` | Read saved and effective tool policies. |
  | `PUT /v1/mcp-oauth/connections/{server_id}/permissions` | Change persistent connection or tool policies. |

  Cloud developer tokens cannot use these PUT routes or decision `scope: "always"`. Use a signed-in app session for permanent changes. Paired daemon devices can make these changes.

  A stale permission version returns 409. Enabling thread auto-approval can resolve an eligible pending request. An explicitly denied tool remains denied. Changing the account default does not decide an existing pending approval.
</Accordion>
