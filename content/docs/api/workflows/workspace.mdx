These operations support your conversations and Agents. They use the same Cloud account or daemon workspace as your other requests.

## Choose skills for an Agent

Read `GET /v1/agent/skills` to find available skill names. For example, inspect a document skill before selecting it for a meeting assistant.

Built-in skills are already available. For a marketplace skill, read its detail and install it first. Then save its name in the [Agent's configuration](/api/workflows/agents).

Selecting a missing skill does not install it. Removing a skill does not remove its name from existing Agent configurations.

<Accordion title="Skill endpoints">
  | Method and path | Use |
  | --- | --- |
  | `GET /v1/agent/skills` | List built-in and workspace skills. |
  | `GET /v1/agent/skills/marketplace` | Browse the installable catalog. |
  | `GET /v1/agent/skills/marketplace/{skill_id}` | Read catalog and installation metadata. |
  | `GET /v1/agent/skills/marketplace/{skill_id}/detail` | Review a skill's instructions before installation. |
  | `GET /v1/agent/skills/repo/{skill_id}/detail` | Read a built-in skill's instructions. |
  | `GET /v1/agent/skills/workspace/{skill_id}/detail` | Read an installed skill's instructions. |
  | `POST /v1/agent/skills/marketplace/{skill_id}/install` | Install the selected catalog skill. |
  | `DELETE /v1/agent/skills/marketplace/{skill_id}` | Remove its installed marketplace copy. |
  | `DELETE /v1/agent/skills/workspace/{skill_id}` | Remove the named workspace skill directory. |

  Reading a skill document does not execute it. After removal, update Agents that selected the skill or reinstall it.
</Accordion>

## Organize with labels

Create a label, then use its returned ID in a project's or thread's `label_ids`. For example, one **Customer work** label can group related conversations and projects.

<Accordion title="Label endpoints">
  | Method and path | Use |
  | --- | --- |
  | `GET /v1/agent/labels` | Read the label registry. |
  | `POST /v1/agent/labels` | Create with `name` and optional hex `color`. |
  | `PATCH /v1/agent/labels` | Send `id` with a changed `name`, `color`, or `order`. |
  | `DELETE /v1/agent/labels` | Remove the query's `id`. Keep its conversations and files. |
</Accordion>

## Check runtime readiness

Input submission starts the runtime when needed. Your integration usually needs no separate wake loop.

| Method and path | Use |
| --- | --- |
| `GET /v1/agent/runtime/status` | Read execution and storage readiness. |
| `POST /v1/agent/runtime/wake` | Start if needed, then wait for readiness without sending a chat message. |
| `POST /v1/agent/runtime/stop` | Release compute while keeping saved workspace data. |

A busy runtime can refuse a stop. Stop active work through its thread or run first. Respect `Retry-After` on temporary readiness errors.

<Accordion title="Reset an entire workspace">
  `POST /v1/agent/workspace/reset` is destructive. It clears conversations, projects, workspace files, and installed or custom workspace skills. It also retires schedules.

  Saved Agents, their knowledge files, and account settings remain. Home is recreated automatically. Reassign Agents from removed projects before reopening their conversations. Reinstall the workspace skills they need.

  Use individual file, thread, or project deletion for targeted cleanup.
</Accordion>
