Select an Agent in the sidebar to return to its main conversation. The header shows the Agent's name without an extra chat title. Its separate setup conversation is labelled **Manager**.

Keep talking to the Agent as the work develops. You do not need to create a new conversation after each task or saved setup change.

## Give follow-ups while it works

Sending a message during a run adds it to the queue above the composer. Each queued message waits for its own turn. **Edit** changes it; **Cancel** removes it.

Use **Send now** to bring a queued correction into the work already running. If that work has finished, the message starts a new turn instead.

> *"Use the revised launch date in this attachment. Keep the investigation so far, but recheck every deadline against Friday."*

A queued message using a different saved Agent setup shows **Saved setup applies next turn** instead of **Send now** while the older turn is running.

**Stop** stops the current run and pauses queued follow-ups. A failed run also pauses them. Use **Send now** on a paused message when you are ready to continue. Reloading or changing devices does not discard the server's queue.

See [Chat](/features/chat#while-fluso-is-working) for the queue controls.

## Let the Agent organize independent work

For a complex request, the main conversation can delegate complementary tasks to sessions while continuing its own work. It should keep the central decisions and combine the results into your deliverable.

For a release review, separate sessions might inspect test evidence and customer-impact notes while the main conversation evaluates release criteria. Small tasks or edits to the same file may be better kept together.

| Session type | Starting context |
| --- | --- |
| Fresh | Its assignment and the necessary inputs, without the main conversation's transcript |
| Forked | Completed conversation context at the point of the fork, followed by its assignment |

Both use the Agent setup selected when they are created and can use shared files and project memory. A fork does not copy running work or routines. Later messages and setup changes do not automatically propagate to an existing session.

The main conversation can reuse a session, send corrections, cancel obsolete work, and request a result. Requested results return automatically. A delegated session cannot create more sessions.

## Inspect sessions when useful

When sessions exist, **Sessions** appears above the composer. It shows work that is queued, working, waiting for approval, idle, or needs attention. A fork icon marks inherited conversation context; **Uses an earlier setup** identifies a session created before a setup change.

Open a session to inspect its conversation. **Main conversation** takes you back. You can rename, archive, restore, or delete delegated sessions from their menus.

- **Idle** means it has no active work. It may be reused or woken by a routine.
- **Archive** organizes the list; use the routine controls to pause future work.
- **Delete** removes the session and its routines. Preserve any results you still need first.

The main conversation remains for the Agent's lifetime. The Manager is separate from this Sessions list.

## Approval and recovery

A session waiting for approval is waiting for your decision. Its approval can appear above the main composer's controls, in the session itself, or in [Inbox](/developers/inbox). A session's report cannot approve an action on your behalf.

Switching away from a chat does not itself stop server work. Long conversations may be compacted into a summary, so reopening a chat does not mean every old message is loaded verbatim into the model.

If a run fails, inspect the error and any files or app changes already made before retrying. Retrying is not a rollback of completed actions. For incomplete work, give a concrete continuation request:

> *"Check the saved findings and source files. Continue from the unfinished checks without repeating completed external actions, and tell me what remains unresolved."*

Use the Manager when the repeated problem is the Agent's instructions. Use connection, approval, or routine controls when the problem is access or scheduling.
