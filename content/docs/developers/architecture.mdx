Fluso separates the client, platform records, runtime compute, and durable user files. This explains why you can leave a chat, return to queued work, and reuse an Agent without rebuilding its setup.

<ArchitectureDiagram />

## From a message to a result

1. The client sends an authenticated message with its conversation and request IDs.
2. The backend checks identity and usage, then forwards work through the gateway to the user's runtime.
3. The runtime admits the request into the conversation's durable queue. A session worker runs the turn with its accepted Agent setup.
4. Tools read or change workspace files and call connected apps through MCP, subject to access and approval rules.
5. Progress streams to the client. History and request state let it recover after a connection drops.

A main Agent conversation and its Manager have separate histories. The Manager edits one Agent's setup; the main conversation performs its work and coordinates delegated sessions.

## What is stored where

| Boundary | Durable state |
| --- | --- |
| Platform database | User and access records, app connections, routine schedules, public share records |
| User storage | Agent definitions, knowledge files, projects, skills, conversations, request ledgers, and queues |
| Project working memory | Bounded summaries and evidence-backed observations within that project |
| External apps | Their own data and actions; selected results may be copied into Fluso by the requested work |

Runtime compute can be suspended or replaced without deliberately deleting those stored records. Current deployment paths include local Docker, AWS ECS, and MicroVM runtimes with ZeroFS storage. Availability depends on the deployment.

## Configuration and context are different

A saved Agent edit creates a new configuration. The main conversation uses it on its next turn; active turns and existing delegated sessions keep the setup they accepted. Skill files and project files remain live shared resources.

Separate conversations do not imply separate private filesystems. Agents within one user's workspace can use its shared files. Project context and knowledge selection guide the model; they are not a filesystem security boundary.

## Routine and result delivery

The scheduler sends a due routine through normal request admission using a stable ID for that occurrence. A busy conversation queues it. The scheduler avoids another overlapping occurrence of the same routine, retries temporary delivery failures, and records problems for Inbox.

Delegated sessions return requested results to their parent. The main conversation must still reconcile those results with the user's latest direction and actual files. A returned report does not grant approval for a new action.

## Recovery is not rollback

A dropped stream does not prove a run failed. The client reconciles with saved history and status. Runtime recovery can resume interrupted work, but an external action that already succeeded is not automatically undone.

Use conversation history, routine state, and [run status](/developers/api-ref/runs) to distinguish queued work, approval waits, failures, and completed output. Avoid resubmitting an uncertain operation under a new ID without checking it.
