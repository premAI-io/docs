This reference documents the routes used by Fluso clients on the current development branch. It is not a promise that every feature is enabled in every deployed build. These beta contracts may change.

Use the API host and authenticated session for the same environment. Production uses `https://api.fluso.ai`; development clients must use their development API and identity environment.

```bash
export FLUSO_API='https://<your-environment-api-host>'
export FLUSO_TOKEN='<valid-user-access-token>'

curl "$FLUSO_API/v1/auth/me" \
  -H "Authorization: Bearer $FLUSO_TOKEN"
```

Keep tokens out of logs and source control. A token acts for its authenticated user; supplying another user's IDs does not grant access. An `X-API-Key` header alone is not a replacement for the bearer session on these workspace proxy routes.

## Read the authenticated identity

<Endpoint method="GET" path="/v1/auth/me" />

Returns `user` and `api_key_id`. The latter is an identifier, not a secret API key.

```json
{
  "user": {
    "id": "22222222-2222-4222-8222-222222222222",
    "email": "developer@example.com",
    "name": "Developer",
    "picture": null,
    "created_at": "2026-10-08T09:00:00"
  },
  "api_key_id": "33333333-3333-4333-8333-333333333333"
}
```

## Client sign-in is not generic CLI onboarding

The backend has `/v1/auth/client/start`, `/complete`, `/exchange/{code}`, and `/refresh` routes for client handoff. The current frontend's completed handoff supports Telegram. Registering an arbitrary `client: "cli"` does not produce a working browser-to-CLI flow.

For the supported product flow, use [Telegram setup](/remote/telegram). For another integration, confirm its sign-in and token handling with [support](mailto:support@premai.io) before building against the beta routes.

A supported client exchanges a short-lived, single-use code for an access token and refresh token bound to its client identity. `POST /v1/auth/client/refresh` accepts `{"refresh_token": "..."}` and returns refreshed credentials and `api_key_id`.

## Read failures correctly

| Response | Meaning |
| --- | --- |
| `401` | Missing, invalid, or expired authentication |
| `403` | The authenticated user is not allowed to perform the operation |
| `404` | The requested resource is unavailable to this user |
| `409` | A state conflict requires inspection, such as a stale Agent revision |
| `429` | A rate or usage limit was reached; respect retry guidance |
| `502` / `503` | A service or runtime is unavailable; an interrupted write may still need verification |

Do not treat a network failure as proof that a write did not happen. Use operation-specific IDs and reread state before repeating work.
