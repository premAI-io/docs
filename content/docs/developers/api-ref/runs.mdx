Submitting an input returns a receipt with `thread_id`, `input_id`, and `run_id`. Save all three. **202 means accepted, not completed.**

Read `GET /v1/threads/{thread_id}/runs/{run_id}` to check progress. Read `GET /v1/threads/{thread_id}/state` for queued work and pending actions.

## Understand the status

| Status | What to do |
| --- | --- |
| `queued` or `running` | Wait, then read again. |
| `waiting_action` | Read the pending approval or connection request in thread state. |
| `held` | Inspect the state and queued inputs before resuming. |
| `completed` | Read all saved result pages and check the answer. |
| `failed` or `cancelled` | Read the error and any saved results before submitting more work. |

A completed run can contain a failed tool call. A failed run can still have changed an external service. Check the results against the requested task.

## Recover after a timeout

- If the submission response was lost, retry the same body with the same `Idempotency-Key`.
- If you received a receipt, read that run and its [saved items](/developers/api-ref/threads-and-messages#read-message-history).
- If a stream closes, reconnect for new events and read saved state for missed results.

A client timeout does not cancel work. Creating a new key can start another execution.

Input retry receipts remain until 24 hours after completion. After that, inspect the saved run before deciding whether to submit new work. Runs remain readable until their conversation is deleted.

<Accordion title="Thread created, but the first input failed">
  An error from `POST /v1/threads` can include `error.details.thread_id`. Save that ID and inspect the thread state. Its presence does not prove input acceptance.

  After resolving the cause, send the original input and key to that thread's `/inputs` endpoint. This can recover an uncertain acceptance within the retry window.
</Accordion>

## Stop work

Use `POST /v1/threads/{thread_id}/runs/{run_id}/cancel` for one run. Use `POST /v1/threads/{thread_id}/stop` for the conversation.

Read the state until execution stops. A cancellation acknowledgement does not prove that a tool has stopped, and cancellation cannot undo a completed external action.

Use the **Recovery and cancellation** examples in your [workspace's full reference](/developers/api-ref/authentication#choose-your-workspace) for retries, held inputs, and cancellation.
